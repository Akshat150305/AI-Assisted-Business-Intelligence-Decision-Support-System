> **All data is synthetic.**

## 1. Star schema

```
dim_date ──┐
           ├──▶ fact_sales  (one row = one order line)
dim_product ┤
dim_customer ┘
dim_date ──▶ anomaly_weekly (by week_start)
```

Why a star schema: slicers on a small dimension table filter the large fact table in one direction, DISTINCTCOUNT and time-intelligence behave predictably, and the model stays fast and easy to explain.

## 4. Relationships (Model view)

| From (one side) | To (many side) | Cardinality / filter direction | Purpose |
|---|---|---|---|
| `dim_date[date]` | `fact_sales[order_date]` | One to many, single direction (one side filters many side) | Lets the date slicer and time intelligence filter sales. |
| `dim_product[product_id]` | `fact_sales[product_id]` | One to many, single direction (one side filters many side) | Brings category and product name onto sales. |
| `dim_customer[customer_id]` | `fact_sales[customer_id]` | One to many, single direction (one side filters many side) | Brings region and segment onto sales. |
| `dim_date[date]` | `anomaly_weekly[week_start]` | One to many, single direction (one side filters many side) | Lets the date slicer filter the weeks shown on the anomaly page. |

Leave these tables **without relationships**: `findings`, `kpi_summary`, `kpi_monthly`, `customer_metrics` (`findings` is a finished text table; the other three are the answer key). Do not enable bi-directional filtering anywhere.

## 5. Table and column settings

- Mark `dim_date` as a date table using `dim_date[date]`.
- Sort `dim_date[month_name]` by `dim_date[month_number]`.
- Sort `dim_date[day_name]` by `dim_date[day_of_week_number]`.
- Hide the raw numeric columns of `fact_sales` (revenue, cost, profit, quantity, unit_price): users should use the measures. Hide key columns used only for relationships.
- Hide the three answer-key tables from the report view.
- `anomaly_weekly[is_anomaly]` must have type **True/False** (Power Query normally detects it).
